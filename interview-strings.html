Strings & Immutability Interview Questions

Strings & Immutability - topic bank

Topic bank #4 of the Interview Prep hub. Tutorial: Strings · Archive: String classes.

1. Why is String immutable?

Design decision with recursive benefits: safe to share/cache (string pool), thread-safe by default, safe as HashMap keys (hash cached), enables security guarantees (class names, file paths can't be changed mid-operation). Cost: new objects per modification - hence builders. Immutability is enforced by final class, private final char[]/byte[] (9+), no mutators, defensive copies in constructors.

2. The string pool - what goes in it?

A runtime-managed table of unique String literals (and interned strings), in the heap since 7. Literals and compile-time constants are interned automatically; new String("x") creates a heap object plus reuses the literal; intern() adds/moves a String into the pool on demand. Pool allows identity comparison shortcuts inside the JDK and saves memory for repeated literals.

3. == vs equals for Strings - the sure-fire rules?

==: same object reference - true for same literal/constant expression, false for runtime-built strings (unless interned). equals: character content. Interview staple: "a" + "b" == "ab" is true (compile-time constant folding), but String ab = "a"; "a" + "b" == ... hmm: only final/constant variables fold - a plain local does not, so runtime concat → false.

4. How many String objects are created by String s = new String("abc");?

Typically two: the interned literal "abc" (or reuses an existing one) and the new heap String. If "abc" was already in use elsewhere, only one new object. Real interview intent: show you know literals live in the pool and new bypasses reuse.

5. StringBuilder vs StringBuffer vs String concat?

String: immutable - each concat allocates. StringBuilder: mutable, not synchronized, fastest for single-thread building. StringBuffer: same API, methods synchronized - legacy, only for shared mutable buffers (rare). Compiler concat today compiles to invokedynamic makeConcatWithConstants (Java 9+), optimized per call site - explicit StringBuilder still clearer in loops.

6. What changed internally in String across Java versions?

Java 9 (JEP 254, Compact Strings): internally byte[] + coder flag - Latin-1 strings take half memory (big win for heaps full of ASCII). 15: text blocks. 17+: stripIndent/translateEscapes on the text-block API. Recent: template strings (21 preview) for safe interpolation.

7. Text blocks - rules that trip people?

Opening """ must be followed by a newline; incidental whitespace stripped based on the least-indented line + closing delimiter position; escapes still work; \s keeps trailing spaces; \ at line end suppresses the newline; formatted/String.format for substitution. Best for SQL/JSON/HTML blobs - no more \n" + chains.

8. char vs code point - the unicode realities?

char is a UTF-16 code unit: supplementary characters (emoji) need two chars (surrogate pair). Length/charAt/indexOf operate on code units - so "😀".length() == 2. Correct handling: codePointAt/codePoints(), String.length not for user-visible counts, and grapheme clusters (family emoji) need ICU-level libraries. This is the classic "reverse my string" trap.

9. How do you compare strings ignoring case / locale-safely?

equalsIgnoreCase is fine for ASCII-ish identifiers; UI/locale work needs Collator (Collator.getInstance(locale)) and compareTo variants, plus toUpperCase(Locale.ROOT) instead of default-locale (Turkish "i" → "İ" dotless breakage - the famous locale bug). Also normalization (NFC/NFD) before comparison for accented text.

10. split() and regex quirks?

Argument is a regex - "." splits everything (use "\\."); trailing empty strings are dropped (split(regex, -1) keeps them); limit=1 = no split; splitting on a huge string repeatedly recompiles the pattern - precompile Pattern for loops. Special chars: |.^$?*+()[]{}\ need escaping.

11. trim() vs strip()?

trim(): removes chars <= U+0020 (legacy definition). strip() (Java 11): Unicode whitespace via Character.isWhitespace; also stripLeading/stripTrailing. For user input use strip; note it still doesn't remove zero-width chars - those need explicit filtering.

12. String.format vs StringBuilder vs MessageFormat?

String.format: printf-style, locale-aware, allocates a Formatter per call, %s/%d/%f/%n + width/precision. MessageFormat: positional {0} with plurals/choices - for user-facing templates. StringBuilder: fastest raw assembly. Interview point: format strings are nice for logs but expensive in hot paths (and %d on the wrong type throws at runtime).

13. How to join or repeat strings?

String.join(", ", list) (8+), Collectors.joining in streams (with prefix/suffix), "ab".repeat(3) (11+) instead of loops, String.join handles nulls as "null" literal. For big buffers: stream into StringBuilder/Writer directly rather than building monster intermediate strings.

14. What is a hashCode of a String - cached?

Yes: computed lazily as s[0]*31^(n-1) + ... + s[n-1], cached in the field (historically; in modern JDKs a separate hash field). 31 chosen because odd prime, cheap shift-subtract, few collisions in practice. Empty string hash = 0; "a" = 97; "Aa" and "BB" collide (both 2112) - the classic collision pair demo.

15. Memory: how much does a small string cost?

String object header (12-16B) + byte[] ref + hash + coder ≈ 24B, plus the byte[] itself (header 16B + bytes, padded to 8) ≈ 24B for "abc" - call it ~48B total vs 3 characters of data. Hence: avoid millions of tiny strings (substring-parse parse patterns), use substring sharing removed in 7u6 (always copies now - do not keep references to huge parent via substring).

16. Are lambdas/switch/etc allowed on Strings - what makes switch work?

switch (string) compiles to hashCode + equals checks (since 7) - so it's a hash-based dispatch, not identity: case labels are compile-time constants compared with equals. NPE if the switch value is null (unlike enum switches which also NPE, but with clearer stack).

17. Encodings: how do you convert bytes to String safely?

Always specify the charset: new String(bytes, StandardCharsets.UTF_8); default-charset constructors (platform-dependent) are a portability bug (works on dev Windows, breaks on Linux containers). Files: Files.readString(path, UTF_8) (11+). Watch BOM handling for Windows text files. Same for getBytes.

18. Palindrome check with StringBuilder?

Simplest: sb.toString().equals(sb.reverse().toString()) - but note reverse() reverses code units, breaking surrogate pairs (see unicode q). Robust: two-index loop over code points, or Stream of code points with IntStream range compare. Also normalization/case-insensitivity if "racécar" style inputs appear.

19. Which methods cause surprises with null?

s.equals(null) → false (fine); null.equals(s) → NPE; String.valueOf(null) → "null"; concat with null → "null" text appears in logs (bug source); Objects.toString(o, "default"), Objects.equals(a,b) are the null-safe tools. Validate inputs at boundaries (Objects.requireNonNull) instead of scattering checks.

20. Regex: greedy vs reluctant vs possessive?

Greedy .* takes as much as possible then backtracks; reluctant .*? as little as possible; possessive .*+ no backtracking (faster, can fail where greedy succeeds). Catastrophic backtracking: nested quantifiers on long failing input - the ReDoS attack; fix with possessive/atomic groups, anchors, or non-regex parsing (and validate user patterns/length limits).

21. How do you count words / find word boundaries?

split("\\s+") handles simple cases (beware leading spaces → empty first token; use trim first). Better: BreakIterator.getWordInstance(locale) for real text, Pattern with \b for ASCII identifiers, or Matcher.results() streaming (9+). Define "word" with the interviewer - punctuation, unicode letters, contractions all change the answer.

22. What are the best-practice API habits for strings in code review?

Constants for repeated literals (and no values hard-coded twice); prefer isEmpty()/isBlank() (11+) over length checks; switch over long equals-chains; no string parsing for structured data (use JSON/XML parsers); never build SQL by concatenation; encode explicitly; treat passwords as char[]/byte[] not String (heap dumps/immortality), prefer MessageDigest.isEqual for constant-time comparisons.
