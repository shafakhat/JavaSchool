Collections Interview Questions

Collections - topic bank

Topic bank #2 of the Interview Prep hub. Deep class-by-class tutorials: List classes · Set classes · Queue classes · Map classes.

1. Why does the collections framework exist - what came before?

Before 1.2: Vector, Hashtable, Enumeration, arrays - no common interface contract, every container had its own API, synchronization everywhere. The framework (1.2): interfaces (Collection hierarchy), implementations, algorithms (Collections), iterator protocol, equals/hashCode-based semantics. Generics (5) removed casts; lambdas (8) enabled forEach/removeIf/computeIfAbsent.

2. ArrayList vs LinkedList - the full table?

ArrayList: array-backed, O(1) random access, amortized O(1) add-at-end, O(n) insert/remove-in-middle (System.arraycopy), memory ~contiguous. LinkedList: doubly linked nodes, O(1) insert/remove given the node's position via iterator, O(n) access, huge per-node overhead, poor cache locality. Verdict: ArrayList wins nearly always; use LinkedList as a List almost never - ArrayDeque beats it as a queue.

3. How does ArrayList grow?

Default capacity 10 (on first add), growth oldCapacity + (oldCapacity >> 1) (≈1.5×), then Arrays.copyOf. ensureCapacity/constructor-with-size avoids repeated copies. Note size() vs capacity - trimming via trimToSize(). Removing from the middle shifts the tail left.

4. What does subList return - and the classic trap?

A view: writes into it write through to the backing list; the returned object is a private inner class, not an ArrayList. Structural changes to the original list invalidate the view (ConcurrentModificationException). It doesn't free memory of the original if retained.

5. Iterator remove vs Collection remove?

Only the iterator's remove is legal during iteration (removes the element just returned, updates modCount). list.remove(x) inside a for-each → ConcurrentModificationException on the next step (fail-fast). From Java 8: removeIf expresses it cleanly and often faster (bulk shift).

6. Fail-fast vs fail-safe iterators?

Fail-fast (ArrayList, HashMap): check a modification counter each next() → CME - a bug detector, not a guarantee. Fail-safe (weakly consistent - ConcurrentHashMap, CopyOnWriteArrayList): iterate over a snapshot/stable view, no CME, may or may not see concurrent updates. Neither is "safe" for compound operations - use ConcurrentHashMap atomic methods.

7. What does Collections.unmodifiableList actually prevent?

Writes through that view. Mutations via the original reference still appear - the view is read-only, not the data. Truly immutable: List.of/List.copyOf (Java 10+), Guava ImmutableList. Note List.of throws NPE on nulls and doesn't allow duplicates (that's Set.of).

8. Arrays.asList vs List.of vs new ArrayList?

Arrays.asList: fixed-size view of the array - set ok, add/remove throw UnsupportedOperationException; writes reflect into the array. List.of: immutable, rejects nulls. new ArrayList<>(Arrays.asList(...)) or new ArrayList<>(List.of(...)): independent mutable copy - the usual answer.

9. HashSet internals - what makes add O(1)?

A HashMap with a dummy value: hash → bucket → equals. Average O(1) add/contains. Iteration order is unspecified (bucket order, changes with capacity). LinkedHashSet: insertion order via linked entries (slightly more memory, faster iteration than HashSet). TreeSet: red-black tree, sorted, O(log n).

10. HashMap: put() step by step?

Hash the key (h ^ (h >>> 16) spread → fewer collisions on small tables), index = (n-1) & hash (n power of two), walk the bucket: match on hash + equals → replace; else append (Java 8: tail append). If bucket length ≥ 8 and capacity ≥ 64 → treeify (red-black) for O(log n) worst case; resize at load factor 0.75 (doubles, splits buckets; Java 8 preserves relative order).

11. Why is a bad hashCode a performance disaster but not a correctness bug?

All keys land in one bucket → chains/tree: O(n) or O(log n) lookups instead of O(1). Correctness only needs equals/hashCode consistency. Classic bad hash: constant hash, or hashing only one field of many. Fix: IDE/records hashCode, or Objects.hash (allocates varargs - fine outside loops).

12. Mutable keys in HashMap - what exactly breaks?

Lookup recomputes the hash from the current state; if the hash changed after insertion, the bucket index no longer matches → get returns null even though the object is there (and it's invisible to remove during iteration too). Keys must be immutable, or at least never mutate equals-relevant fields while in the map.

13. TreeMap - what contract does it require?

Sorting requires either Comparable keys or a Comparator; comparing must be consistent with equals ideally (else the map can hold "duplicate-equal" keys that differ only by compareTo). Operations O(log n); magic methods: firstKey/lastKey, floorKey/ceilingKey, headMap/tailMap/subMap (views), descendingMap. Also NavigableMap successor: ConcurrentSkipListMap for concurrent sorted maps.

14. LinkedHashMap as an LRU cache?

Constructor with accessOrder = true moves entries to the tail on access; override removeEldestEntry to evict when size() > capacity. That's a 10-line LRU; for production use Caffeine/Guava for concurrency, weighers, and stats.

15. HashMap vs Hashtable vs ConcurrentHashMap?

Hashtable: legacy, all methods synchronized on one lock - banned in modern code. Collections.synchronizedMap: same coarse locking, nulls allowed, fail-fast iteration requires manual sync. ConcurrentHashMap: lock-free reads, bin-level CAS/synchronized writes, forbids null keys/values, weakly consistent iteration, atomic computeIfAbsent/merge. That's the default for shared maps.

16. Why does ConcurrentHashMap forbid nulls?

Ambiguity: get(k) == null can't distinguish "absent" from "mapped to null" in a concurrent world where you'd check-then-act wrongly. HashMap allows nulls (one null key, many null values) so the distinction is defined there. Result: CHM forces you to model absence explicitly.

17. What is CopyOnWriteArrayList for?

Read-mostly listener/observer lists: reads iterate a snapshot with zero locking; every write copies the whole array (O(n) - never in a hot write loop). Iterators never throw CME and never see later changes. Classic use: listener registries, configuration snapshots.

18. Queue vs Deque vs Stack - which to choose?

Stack is legacy (extends Vector); the modern LIFO is ArrayDeque (push/pop). Use Deque for both ends; ArrayDeque for general use (addFirst/removeLast etc.), LinkedList only if you also need List ops. The Queue methods come in two flavors: throwing (add/remove/element) vs null-returning (offer/poll/peek) - use the latter.

19. PriorityQueue internals?

Binary heap over an array: offer/poll O(log n), peek O(1). Not stable; iteration is heap order, not sorted - use repeated poll or a sort for order. Natural order or Comparator; no nulls. No decrease-key (remove + re-add). Bounded top-K via a min-heap kept at size K.

20. BlockingQueue in producer-consumer?

ArrayBlockingQueue (bounded array), LinkedBlockingQueue (optionally bounded), SynchronousQueue (hand-off), PriorityBlockingQueue, DelayQueue (time-based), LinkedTransferQueue. Producers put (blocks when full), consumers take (blocks when empty); offer(timeout) for back-pressure. This replaces wait/notify hand-rolled code entirely.

21. Comparable vs Comparator in collections - who uses which?

TreeSet/TreeMap use natural order (Comparable) unless given a Comparator in the constructor; PriorityQueue same. Collections.sort/List.sort take either (Comparable if null comparator). sort is stable (TimSort/MergeSort) - equal elements keep insertion order; Arrays.sort on primitives is dual-pivot quicksort (unstable, no comparator).

22. How do you sort a map by values?

Stream: map.entrySet().stream().sorted(Map.Entry.comparingByValue()).collect(toLinkedHashMap()) - must collect to a LinkedHashMap or the sort is lost. Alternatives: sort the entry list, or build a TreeMap with a value comparator (breaks map contract - use entries instead). Tie-break with thenComparingByKey() for determinism.

23. What does Collections.rotate/shuffle/binarySearch require?

binarySearch: the list must be sorted by the same comparator you pass, ascending; otherwise undefined result (it returns a bogus index, not an error). shuffle: you can pass a Random for reproducibility (tests). rotate: distance semantics - positive rotates right. frequency, disjoint, min/max, nCopies, singletonList are the other workhorses.

24. What's the difference between Collection and Collections?

Collection: root interface of the hierarchy (except Map). Collections: utility class - algorithms (sort, binarySearch, shuffle), wrappers (unmodifiable/synchronized/checked), factories (emptyList, singleton). Also Collection has no Map - they're separate hierarchies; Map is a key-value structure, not a collection of values, though map.values() is one.

25. How is Set uniqueness enforced with custom objects?

Via equals/hashCode (HashSet) or compareTo (TreeSet). Miss either → duplicates slip in: forgetting hashCode entirely means equal objects hash differently → separate buckets. Debug trick: put two "equal" objects and print size(); then check hash consistency.

26. What's the deal with Map.getOrDefault, computeIfAbsent, merge?

Modern idioms that replace get-then-put races: map.computeIfAbsent(k, k -> new ArrayList<>()).add(v) (multi-map), map.merge(k, 1, Integer::sum) (counting), getOrDefault (read). They're atomic on ConcurrentHashMap (the function runs under the bin lock - don't do long work/call other maps inside).

27. What implementations would you pick for: cache, leaderboard, word frequency, LRU, task queue?

Cache: Caffeine (or CHM + TTL). Leaderboard: TreeMap<Score, Set<Player>> or skip list. Word frequency: HashMap<String,Long> + merge. LRU: LinkedHashMap accessOrder or Caffeine. Task queue: BlockingQueue (bounded) behind an executor; PriorityBlockingQueue for priorities.

28. How do you make a collection thread-safe properly?

Choose the right class first (CHM, CopyOnWrite, BlockingQueue, ConcurrentSkipListMap). Collections.synchronizedX wrappers make single calls atomic but iteration still needs synchronized(list) {...}; compound operations (check-then-add) need external locking or atomic APIs. Immutable collections avoid the problem entirely - share freely.

29. What changed in collections across versions?

5: generics. 6: Deque/ArrayDeque/NavigableMap. 7: diamond, fork/join helpers. 8: streams, lambdas, Map default methods, removeIf. 9: List.of/Set.of/Map.of immutables. 10: copyOf. 11: toArray(IntFunction). 16: Stream.toList. 21: sequenced collections (getFirst/getLast), toArray unchanged... plus virtual-thread-friendly queues (unrelated but concurrent).

30. Whiteboard: find duplicates in a list - what does the choice of collection prove?

HashSet<T> streaming with add return value - O(n), clean: it demonstrates you know hashing, that add returns boolean, and that you can early-exit. If order must be preserved: LinkedHashSet. If counting matters: HashMap merge. If memory-bound: sort first (O(n log n), O(1) extra) then scan adjacent. Interviewers watch which you pick and why.
