JDBC & Database Interview Questions

JDBC & Database - topic bank

Topic bank #6 of the Interview Prep hub. Tutorials: JDBC · archive Database examples.

1. JDBC architecture in one breath?

Application → JDBC API (java.sql) → driver manager / DataSource → driver (type 4 pure-Java socket driver) → database wire protocol. The API is a thin abstraction; the driver translates to vendor protocol. Connections, statements, result sets are the three core types - all AutoCloseable.

2. DriverManager vs DataSource?

DriverManager: legacy, you hard-code URL/credentials, opens a raw connection per call - not poolable. DataSource: factory interface implemented by pools (HikariCP, Tomcat JDBC, dbcp); configured in app servers/Spring, supports JNDI lookup and pooling. Modern answer: always DataSource, never DriverManager in server code.

3. What does a connection pool actually manage, and what's the cost of getConnection?

Pool: pre-opened physical connections, borrow/return with validation, eviction of idle/leaked ones, limits (maxPoolSize). getConnection borrows (fast, ~µs) instead of TCP+auth handshake (ms). Key knobs: max pool <= DB max_connections ÷ instances, connectionTimeout, maxLifetime (below DB wait_timeout), leak detection threshold.

4. Why PreparedStatement - security AND performance?

Security: parameters are sent separately from SQL text → injection impossible for values (not for identifiers). Performance: the DB can cache the execution plan; repeating the statement with new parameters reuses it. Also type-safe setters (setInt, setDate...) and no escaping bugs. Statement concatenation is an instant fail in review.

5. Where does PreparedStatement caching live - the driver pool story?

Three layers: (1) app-side statement cache (HikariCP statementCacheSize) per connection, (2) driver's server-prepared statements, (3) DB's plan cache. Cheap vs expensive plans, useServerPrepStmts (MySQL default false, prepared at client), and memory on the DB side all matter for tuning.

6. Transactions: what does setAutoCommit(false) actually change?

All statements until commit/rollback form one unit; without it each statement auto-commits. Pattern: try { conn.setAutoCommit(false); ...work...; conn.commit(); } catch { conn.rollback(); throw; } finally { conn.setAutoCommit(true); } - or let the framework (@Transactional) do it. Pooled connections are returned between transactions; leaked autoCommit=false state is a classic pool bug.

7. Isolation levels - what anomalies do they stop?

READ UNCOMMITTED: allows dirty reads. READ COMMITTED: prevents dirty, allows non-repeatable (same row re-read differs). REPEATABLE READ: prevents non-repeatable, allows phantom rows in some DBs (MySQL InnoDB's RR also blocks phantoms via gap locks). SERIALIZABLE: all prevented, lowest concurrency (often snapshot-based). Defaults: MySQL RR, Oracle/Postgres Read Committed.

8. Lost update problem and its fixes?

Two transactions read a value and both write based on the old one - one update is lost. Fixes: optimistic locking (version column, compare-and-set UPDATE ... WHERE version = ?, retry on 0 rows), pessimistic locking (SELECT ... FOR UPDATE), or atomic SQL (SET balance = balance - ?). Interview favorite: explain the version-column flow.

9. What are savepoints?

Named mid-transaction markers: rollback to a savepoint to partially undo work while keeping the transaction alive. Used by nested transaction emulation in frameworks (Spring NESTED propagation) and batch retries - think "partial rollback without losing the whole unit of work".

10. Batch updates - when and how?

When inserting/updating many rows: addBatch() repeatedly, then executeBatch() (chunked, e.g. 500-1000) - cuts round trips and can be 10-50× faster. Driver flag matters (MySQL rewriteBatchedStatements=true). Check BatchUpdateException.getUpdateCounts() and remember: within a transaction a partial batch failure rolls back everything if not handled per-chunk.

11. ResultSet scrolling and fetch size?

Default TYPE_FORWARD_ONLY - one pass. CONCUR_READ_ONLY handles most needs; updatable/scrollable sets are driver-dependent. Fetch size (rows buffered per network round trip) is a huge perf lever: default often loads everything for MySQL (set useCursorFetch/Integer.MIN_VALUE streaming with care). Close in try-with-resources; getters by column name are readable but slower than by index.

12. NULL handling in JDBC?

setNull(i, Types.INTEGER) for inserts; wasNull() after a getter to know if the column was SQL NULL (0 vs NULL ambiguity for primitives); getObject returns null for reference types; getInt on NULL returns 0 - a silent bug source. In SQL, remember NULL = unknown: WHERE col = NULL never matches, use IS NULL; aggregates skip NULLs (COUNT(col) vs COUNT(*)).

13. Which SQLException information matters for retries?

getSQLState (5-char standard state, e.g. 40001 serialization failure, 08xxx connection), getErrorCode (vendor), getNextException chain. Retry only on transient classes: deadlock/serialization failures, connection blips - with bounded retries + backoff, and idempotency awareness (don't retry a non-idempotent insert blindly).

14. How do you handle BLOBs/CLOBs?

Stream them (getBinaryStream/getCharacterStream) rather than byte[] for large data; PostgreSQL uses large objects + OID/lo_import (JDBC Blob support quirks), Oracle uses BLOB locators with row locking for updates. General advice: keep big files in object storage, store keys in the DB; if you must, stream with setBinaryStream and avoid SELECTing the column in list queries.

15. CallableStatement - stored procedures?

connection.prepareCall("{call proc(?, ?)}"), set IN params, registerOutParameter for OUT, execute, read with getters matching the registered Types. Best for set-based work in the DB (bulk ops, reporting) where moving data to the app is wasteful. Portability and version-control of procedures are the trade-offs.

16. How do you avoid N+1 selects?

Detect via SQL logging/count per request. Fixes: join fetch (one query returning duplicated parent rows), batch fetching (WHERE id IN (...)), eager fetch only where needed, and DTO projection queries (SELECT new Dto(...) in JPQL). Frameworks' lazy loading defaults are the usual culprit - manage fetch plans deliberately (Hibernate @BatchSize, join fetch, entity graphs).

17. Connection leaks - how do you find and prevent them?

Symptoms: pool exhaustion ("connection timeout" errors), DB sessions piling up. Find: pool metrics + leakDetectionThreshold, DB-side pg_stat_activity/processlist. Prevent: always try-with-resources, never hold connections across user think-time/HTTP calls, close in finally, keep transactions short, and wrap raw JDBC in frameworks' templates that manage resources.

18. What is a savepoint-free alternative to nested transactions, and what's XA?

Spring-style propagation joins the outer transaction (no real nesting - REQUIRES_NEW suspends the outer). XA/distributed transactions coordinate two-phase commit across DBs/JMS - heavyweight and rarely worth it; prefer saga/outbox patterns with idempotent steps instead of 2PC for microservices.

19. RowSet and modern alternatives - still relevant?

RowSet (CachedRowSet, JdbcRowSet) adds JavaBean-style navigation and disconnected operation - mostly superseded by modern ORMs/query libraries (Spring JdbcTemplate, jOOQ, MyBatis). Know what a JdbcRowSet is (thin ResultSet wrapper with properties) for exam trivia, but practical answers are templates/ORM.

20. Design question: write a DAO layer that is testable and safe.

Inject a DataSource (constructor); use one method per use case; PreparedStatement everywhere; try-with-resources nesting (conn → stmt → rs); map rows to records/DTOs; keep transactions outside (service layer) or accept a Connection for units that must join one; validate inputs; log SQLState not full SQL with user data; test with Testcontainers (real DB) rather than mocks of JDBC - mocks test your mock, not SQL.
