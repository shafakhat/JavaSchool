Java Interview Questions - Master List

Core Java & JVM

Click a question to reveal the answer. 115 questions - the set most often asked in Java developer screens.

1. What is the difference between JDK, JRE and JVM?

JVM runs bytecode and is platform-specific. JRE = JVM + core libraries (to run Java). JDK = JRE + compiler and tools like javac, jar (to develop). "Write once, run anywhere" works because the JVM differs per OS while bytecode does not.

2. What does the class file contain?

Version info, constant pool, fields, methods and the bytecode itself, plus a symbol reference table. The magic number CAFEBABE starts every class file.

3. How does the JVM load and link a class?

Loading brings the .class bytes into memory (bootstrap → platform → application class loaders). Linking = verification (bytecode safety), preparation (static fields allocated) and optional resolution (symbol references made concrete). Then initialization runs static blocks.

4. What is the difference between path and CLASSPATH?

PATH tells the OS/shell where to find executables (java, javac). CLASSPATH tells the JVM where to find class and jar files; with the default application class loader, the current directory . is implied.

5. What is JIT compilation?

The Just-In-Time compiler turns hot bytecode into native machine code at runtime, with inlining, escape analysis and loop optimizations. It is why Java beats naive interpreters - the profile-guided optimization happens after warm-up.

6. Platform independence - where does it actually live?

At the bytecode level, not the source. You compile once to platform-neutral .class files; each platform's JVM executes them. Native libraries (.dll/.so via JNI) are the escape hatch where portability ends.

7. What is the difference between compile time and runtime?

Compile time: syntax checking, type checking, bytecode generation. Runtime: loading, JIT, memory allocation, exceptions. Errors found at compile time never run; runtime errors (NullPointerException, divide by zero) only appear when the code path executes.

8. How is memory organized in the JVM?

Heap (young + old generations) for objects, metaspace (native memory, since Java 8) for class metadata, stack per thread for frames (locals, operand stack), plus code cache for JIT-compiled code and direct memory for NIO buffers.

9. What is the difference between Stack and Heap?

Stack holds frames of active method calls - primitives and references, fast LIFO, thread-confined. Heap holds all objects and arrays, shared between threads, managed by the GC. Overflowing the stack throws StackOverflowError; an exhausted heap throws OutOfMemoryError.

10. When is an object eligible for garbage collection?

When it becomes unreachable - no live thread can reach it through any chain of references. Local variables going out of scope, cyclic references with no external root, and disconnected listener graphs all become collectible. finalize() is deprecated; use Cleaner or try-with-resources instead.

11. Name the main JVM garbage collectors.

Serial, Parallel (throughput), G1 (default since 9, region-based), ZGC and Shenandoah (sub-millisecond pauses, low latency). Epsilon is a no-op collector for testing. Choice depends on latency SLA vs throughput.

12. What is a memory leak in Java if GC exists?

Objects that are unreachable-but-not (still referenced) accumulate: static collections growing forever, unclosed resources, listener lists never cleared, ThreadLocal in pooled threads, oversized caches. The GC only collects unreachable objects, so a retained reference graph is a leak.

13. What are String pools?

A pool of interned string literals (and results of intern()). "a" == "a" is true because both point at the same pooled instance. In Java 7+ the pool lives in the heap. String literals are compile-time constants, so "a"+"b" folds to "ab".

14. How does Escape Analysis help?

The JIT proves an object never leaves a method → it can allocate it on the stack or eliminate the allocation entirely; it also enables lock coarsening/elision on synchronized blocks. That is why some "obvious" allocations cost nothing in tight loops.

15. What does the transient keyword do?

Marks a field to be skipped by default serialization. Useful for caches, derived fields, secrets and anything not portable across versions. Pair with readObject/writeObject for custom handling, or implement Externalizable for full control.

Object-Oriented Programming

16. What are the four pillars of OOP?

Encapsulation (hide state behind accessors), inheritance (reuse/extend), polymorphism (one interface, many forms), abstraction (model essentials, hide detail). Composition over inheritance is the modern rule of thumb.

17. Abstract class vs interface - today's rules?

Abstract class: state, constructors, any visibility, single inheritance. Interface: contracts, default/static methods, multiple inheritance of type; fields are implicitly public static final. Use an interface for a capability ("can do"), an abstract class for a shared base implementation ("is a").

18. Is Java pass-by-value or pass-by-reference?

Always pass by value. For primitives the value is copied; for objects the reference is copied - the method can mutate the same object, but reassigning the parameter does not affect the caller.

19. Overloading vs overriding?

Overload = same name, different parameter list, resolved at compile time (static). Override = same signature in a subclass, resolved at runtime via the vtable. Constructors cannot be overridden; return type may only covary when overriding.

20. Can you override a private or static method?

No. Private methods are not visible to subclasses; static methods are hidden (resolved by reference type), not overridden. Calling a "hidden" method through a subclass reference still invokes the superclass version.

21. What is polymorphism's dynamic dispatch?

The JVM picks the implementation from the object's actual type at runtime, not the variable's declared type. Virtual methods go through the vtable; interfaces use itable dispatch. final/private/static methods and constructor calls are bound statically.

22. What is the Liskov Substitution Principle?

Subtypes must be substitutable for their base types: no stronger preconditions, no weaker postconditions, no broken invariants. Violations look like a subclass throwing where the parent promised not to, or a Square that breaks Rectangle's area contract.

23. Composition vs inheritance?

Composition builds behavior by delegating to contained objects - flexible at runtime, no fragile base class. Inheritance couples to the parent's internals and is fixed at compile time. Prefer composition; use inheritance for true is-a taxonomies and interfaces.

24. What is an immutable class? Recipe?

State never changes after construction. Recipe: final class, all fields final and private, no setters, defensive copies of mutable inputs/outputs, no this escaping in the constructor. Examples: String, Integer, Instant, records. Immutability gives thread-safety for free.

25. What does final mean in each position?

Variable: reference/value assigned once. Method: cannot be overridden. Class: cannot be extended. It has no direct effect on the internal mutability of the referenced object.

26. What is the diamond problem and how does Java solve it?

A class inheriting two classes with the same method. Java forbids multiple class inheritance entirely; for interfaces, a class must provide one implementation, and a default conflict between two interfaces must be resolved by overriding explicitly.

27. What are sealed classes and why?

sealed (Java 17) restricts which classes may extend an interface/class (permits). Combined with pattern-matching switch, the compiler can check exhaustiveness - a controlled alternative to enums when subtypes carry data.

28. What is a record good for?

Plain, immutable data carriers: equals/hashCode/toString and accessors are generated. Use for DTOs, results and query objects - not for entities with identity or mutable lifecycle. Records cannot extend classes and are implicitly final.

29. What is the "fragile base class" problem?

A base class change silently breaks subclasses: a new method name colliding with a subclass method, changed calling conventions in constructors that invoke overridables, reliance on internal order. Composition and final/template-method discipline reduce the risk.

30. What are access modifiers?

private (same class), default/package-private (same package), protected (package + subclasses), public (everywhere). Module boundaries (Java 9+) add another wall: exports decide which packages are even visible.

Strings

31. String vs StringBuilder vs StringBuffer?

String immutable (safe, shareable). StringBuilder mutable, unsynchronized - use in single-threaded loops. StringBuffer synchronized legacy variant. In loops, concatenation compiles to StringBuilder since Java 5; repeated + in one expression still creates temporaries.

32. Why is String immutable?

Security (classloader paths, file paths, DB URLs can't be tampered), string-pool correctness, thread-safety without locks, and safe use as HashMap keys - a key that can't change can't get lost.

33. == vs equals() vs compareTo()?

== compares references (identity). equals() compares logical content (as defined by the class). compareTo() gives ordering for sorts. Always override equals together with hashCode - equal objects must hash equally.

34. Why does new String("a") == "a" print false?

The literal is interned in the pool; new always allocates a fresh object outside it. Identity differs, content is equal. .intern() returns the pooled instance and would make the comparison true.

35. How does String.intern() work today?

Returns the canonical pooled representation: the literal's object, or (since 7) the heap copy moved/recorded in the pool. Historically used to deduplicate huge string sets; with the pool on the heap the old perf tricks matter much less.

36. How do you safely compare user input to a password-like value?

Use constant-time comparison for secrets: MessageDigest.isEqual(a.getBytes(UTF_8), b.getBytes(UTF_8)) - equals short-circuits on first difference and leaks timing. Better still, store a salted hash (bcrypt/argon2) and compare hashes.

37. What is text blocks for?

Text blocks (Java 15) keep multi-line strings readable: """ delimiters, incidental indentation stripped, escaping on demand. Perfect for SQL, HTML, JSON and log formats - no more \n soup.

38. Are Strings Unicode?

Yes - UTF-16 code units internally, with surrogate pairs for supplementary characters. Beware length() counts code units (an emoji can be 2), and charAt can split a pair. Use codePointCount/offsetByCodePoints for text APIs.

Collections Framework

39. List vs Set vs Map?

List: ordered, indexed, duplicates allowed (ArrayList, LinkedList). Set: unique elements (HashSet, TreeSet, LinkedHashSet). Map: key→value associations (HashMap, TreeMap). Queue/Deque (ArrayDeque, PriorityQueue) cover FIFO/priority processing.

40. ArrayList vs LinkedList - what do you actually pick?

ArrayList almost always: contiguous array, cache-friendly, O(1) random access, amortized O(1) append. LinkedList pays pointer overhead per node, loses on memory locality and loses on get; it only wins for heavy mid-list insert when you already hold the ListIterator.

41. HashMap internals?

Array of buckets + linked lists (bin), turning into trees (≤8 nodes, and table ≥64) when collisions pile up - red-black trees give O(log n) worst case. Hash spread with hash ^ (hash>>>16); capacity is always a power of two; default load factor 0.75 triggers resize.

42. Why must hashCode and equals be consistent?

HashMap finds the bucket by hash, then the entry by equals. If equal objects hash differently, the entry lands in another bucket and is never found. Contract: equal ⇒ same hash; same hash ⇒ not necessarily equal; equals must be reflexive/symmetric/transitive/consistent.

43. Hashtable vs HashMap vs ConcurrentHashMap?

Hashtable: legacy, whole-map synchronized, unsized. HashMap: unsynchronized, fastest single-thread. ConcurrentHashMap (Java 8+): lock-free reads via volatile/CAS, per-bin locking on write - the default for concurrent code; also has computeIfAbsent atomic ops.

44. How do you iterate a HashMap?

for (var e : map.entrySet()) for values+keys, map.forEach((k,v) -> ...), or map.values()/keySet() when only one side is needed. Never mutate structure during iteration or you get ConcurrentModificationException - except via Iterator.remove or the map's own remove.

45. TreeMap vs LinkedHashMap?

TreeMap: sorted by key (or comparator), O(log n) ops, NavigableMap extras (headMap, ceilingKey). LinkedHashMap: insertion (or access) order, O(1), enables LRU caches via removeEldestEntry or access-order iteration.

46. Comparable vs Comparator?

Comparable is the class's natural ordering (compareTo, one per class). Comparator is an external, composable strategy: comparing(Person::name).thenComparing(Person::age) - multiple orders without touching the class.

47. What is a fail-fast iterator?

ArrayList/HashMap iterators track a modCount and throw ConcurrentModificationException on structural change from another source - a quick guard, not a guarantee (it's best-effort). Use CopyOnWriteArrayList or concurrent collections for real multi-thread iteration.

48. Enumeration vs Iterator?

Enumeration is the legacy (Vector/Hashtable) interface: hasMoreElements/nextElement, no remove. Iterator added remove() and is the framework standard - new code should use Iterator or Streams; Enumeration only appears in old APIs and jar/resource listings.

49. What does Collections.unmodifiable vs immutable mean?

unmodifiableList wraps: writes throw, but the backing list can still change. List.of/List.copyOf are truly immutable snapshots: fixed content, null rejected, safe to share. Prefer the real immutable factories.

50. What is the difference between Array and ArrayList?

Arrays are fixed-size, covariant (String[] is an Object[] - runtime ArrayStoreException risk), can hold primitives. ArrayList is resizable, generics-erased (no store exception, rethinks at compile time), objects only (autoboxing for ints).

Threading & Concurrency

51. Process vs thread?

A process has its own address space, files and security context; threads of a process share that memory and resources but have their own stack and program counter. Threads are cheaper to create/switch; a process crash isolates, a bad thread can corrupt shared state.

52. Ways to create threads?

Thread subclass, Runnable passed to Thread, Callable+FutureTask (returns a result/throws), thread pools via ExecutorService, CompletableFuture, parallel streams, and virtual threads (Java 21). Production code: executors or virtual threads - never raw threads.

53. start() vs run()?

start() creates a new OS thread and calls run() on it (one start only - second call throws). Calling run() directly is just a method call on the current thread - no concurrency at all, a classic interview trap.

54. What is a race condition?

Outcome depends on uncontrolled interleaving: read-check-write on shared state, check-then-act in HashMap, lazy init without sync. Fix with locks, atomic classes, immutable data, or confinement - don't rely on "it works on my machine".

55. synchronized vs volatile?

volatile: visibility + ordering only - reads see latest write, no reordering across it; no mutual exclusion, i++ is still unsafe. synchronized: mutual exclusion + the same memory guarantees (lock releases flush, acquires reload). Use volatile for flags/handoff, locks for compound actions.

56. What is deadlock and how do you prevent it?

Two threads waiting on each other's locks, forever. Prevention: consistent global lock ordering, try-lock with timeout (lock.tryLock(1, SECONDS)), shrink lock scope, avoid nested locks, or use higher-level concurrency (ConcurrentHashMap, actors). jstack/jcmd thread dumps show "found one Java-level deadlock".

57. What is the Java Memory Model's happens-before?

A visibility ordering: if action A happens-before B, B sees A's writes. Key edges: program order, monitor unlock→lock, volatile write→read, thread start→first action, final field freeze. Without an edge the JIT may reorder or cache - this is the theory under synchronized/volatile.

58. wait() vs sleep() vs join()?

wait(): must hold the monitor, releases it, needs notify/notifyAll, resumes on re-acquire. sleep(): any thread, keeps locks, just pauses. join(): waits for that thread's death (implemented with wait on the Thread object).

59. notify() vs notifyAll()?

notify() wakes one arbitrary waiter; notifyAll() wakes all, who then race for the monitor. With multiple conditions/roles sharing one monitor, notify can wake the wrong thread repeatedly - notifyAll is the safe default unless predicates guarantee only one can proceed.

60. Producer-consumer in one breath?

A shared bounded buffer: producer blocks when full, consumer blocks when empty. Java options: BlockingQueue (ArrayBlockingQueue, LinkedBlockingQueue, SynchronousQueue) where the queue is the synchronization; or wait/notify with explicit lock and condition predicates.

61. ThreadLocal - what and why not overuse?

Per-thread variable: each thread sees its own instance (typical: SimpleDateFormat, request context, transaction handles). Danger: pooled threads retain values → leaks and cross-request contamination; always remove() in finally. Virtual threads make ThreadLocal-heavy code memory-hungry.

62. Callable vs Runnable?

Runnable: run(), no return, no checked exceptions. Callable: call() returns V and may throw - submitted to an ExecutorService it yields a Future<V>. Together via invokeAll/invokeAny you get batch results or first-success semantics.

63. Future vs CompletableFuture?

Future blocks: get() waits, no composition, weak cancellation. CompletableFuture is async and composable: thenApply/thenCompose/thenCombine/allOf, callbacks, exception handling - the basis of non-blocking pipelines (Reactor/RxJava are the richer cousins).

64. What are semaphores, latches and barriers?

Semaphore: N permits - limit concurrency (pools, rate limits). CountDownLatch: one-shot wait for N events (start line). CyclicBarrier: threads rendezvous and continue repeatedly (phased simulations). All from java.util.concurrent, built on AQS.

65. Virtual threads vs platform threads?

Platform threads map 1:1 to OS threads (expensive, thousands max). Virtual threads (Java 21) are scheduled onto a small pool: millions of tasks blocked on IO are fine because blocking unmounts the carrier. Great for IO-bound servers; CPU-bound work still wants a smaller platform pool (or structured concurrency).

Exceptions & Language

66. Checked vs unchecked exceptions?

Checked (IOException, SQLException): compiler enforces throws or handling - recoverable conditions the caller must know about. Unchecked (RuntimeException: NPE, ISE): programming defects. Design rule: throw checked only when the caller can actually do something about it.

67. throw vs throws?

throw raises an actual exception instance (throw new IllegalArgumentException(...)). throws declares possible exceptions in a method signature for the compiler.

68. try-with-resources vs finally?

TWR (Java 7+) closes each AutoCloseable in reverse declaration order automatically, and (since 9) reuses effectively-final existing variables. Exceptions in the body are suppressed-not-lost (addSuppressed). finally stays for locks/non-resources; never put return inside finally.

69. Can you catch an Error like OutOfMemoryError?

Technically yes (it's a Throwable), practically no: Errors signal unrecoverable JVM/system conditions. Don't swallow them; let the process die and alerting fire. Same spirit for StackOverflowError and linkage Errors.

70. What is exception chaining?

Wrapping a low-level cause while preserving it: new ServiceException("save failed", ex) or initCause. The stack trace keeps the root - never replace a cause with a bare new Exception("error").

71. What happens if a finally block returns?

The method returns from finally, silently swallowing any pending exception and discarding the original return value - a classic bug. Avoid return/break/continue in finally (the compiler warns; try-with-resources removed the need).

72. Multi-catch and precise rethrow?

catch (IOException | SQLException e) handles alternatives with one body (e is effectively final). With Java 7 precise rethrow, catch (Exception e) { throw e; } only propagates the actually thrown checked types - no blanket throws clause needed.

Generics, Reflection, Lambdas & Streams

73. Why generics? Type erasure?

Generics give compile-time type safety and remove casts. Erasure: type parameters exist only at compile time - List<String> becomes raw List plus casts/bridges. Consequences: no new T(), no instanceof List<String>, arrays of type parameters impossible - but full binary compatibility with pre-generics code.

74. What are wildcards? PECS?

<? extends T> read-only producer of T; <? super T> write-only consumer of T; <?> unbounded. PECS - Producer Extends, Consumer Super: copy(List<? extends T> src, List<? super T> dst) types collections you read from and write to correctly.

75. Bounded type parameters?

<T extends Comparable<T>> constrains T to types usable by the algorithm, letting the body call t.compareTo without casts. Multiple bounds: <T extends A & B > (class bound first). This is how Collections.sort stays type-safe.

76. What is a lambda expression under the hood?

Syntactic sugar for an instance of a functional interface (single abstract method). Non-capturing lambdas are cached singletons; capturing lambdas generate/define a class implementing the interface, with captured locals stored as fields. this inside a lambda is the enclosing instance.

77. Lambda vs anonymous class?

Same interface targets, differences: lambdas are scope-polymorphic (one generated class per state shape), can't declare fields, this = enclosing object, faster to parse. Anonymous classes define a real named class subtype with their own state and identity.

78. Stream vs Collection?

Collections are data (store, traverse, mutate now). Streams are computation (describe a pipeline, evaluate lazily once on terminal op). No storage, no removal, elements not modified by the stream - that's why stream().forEach(list::add) is an anti-pattern.

79. Lazy vs eager evaluation in streams?

filter/map/limit are lazy - nothing runs until a terminal op (collect/forEach/reduce). That's why limit short-circuits: generate(infinite).limit(10) is safe while eager mapping would hang. Intermediate ops return new streams, single-use.

80. Intermediate vs terminal operations?

Intermediate: return streams, are lazy, may be fused (map+filter compiled into one pass). Terminal: trigger execution, produce a result/side effect, consume the stream. Stream can have many intermediate ops, exactly one terminal.

81. Parallel streams - when?

Only for large, CPU-bound, order-insensitive work on an immutable-ish data source; the common ForkJoinPool gets saturated (it shares with parallelCount logic) and blocking IO inside is poison. For IO use virtual threads/executors; when in doubt, measure - parallel often loses on small inputs.

82. What does reflection allow? Cost?

Inspect classes at runtime (fields/methods/annotations), create instances, invoke methods, even touch private members (setAccessible). Costs: slower than direct calls, defeats static checks (strings instead of symbols), breaks under module encapsulation, and complicates GraalVM native-image. Frameworks use it; business code rarely should.

83. What are annotations and meta-annotations?

Compile/runtime metadata: @Override, @Deprecated, custom @Route, framework markers. Meta-annotations annotate annotations: @Target, @Retention (SOURCE/CLASS/RUNTIME), @Inherited, @Repeatable. Runtime processing uses reflection; APT (Abstract Processor) generates code at compile time (MapStruct, Dagger).

Java 8–21

84. What did Java 8 give us?

Lambdas, method references, the Stream API, default/static interface methods, Optional, new date/time (JSR-310), CompletableFuture, functional interfaces (Function/Predicate/Supplier), parallel F/J improvements, Nashorn (since removed). The biggest language step since Java 5.

85. Optional - correct usage?

Return type for maybe-absent values: findFirst(), map/filter/orElseGet, orElseThrow. Never as a field, parameter or collection element; don't call get without isPresent. map(x -> x.orElse(...)) or nesting is usually a design smell.

86. Record patterns and pattern matching milestones?

instanceof binding (16), pattern matching for switch (21 - finalized), record patterns (19/21 - destructure case Point(int x, int y)), sealed types (17), virtual threads (21). Together they make data-oriented code concise and exhaustiveness-checked.

87. What is the var keyword?

Local variable type inference (10): the type is still static, just written once from the initializer - var m = new HashMap<String, List<Integer>>(). Not for fields/parameters without initializer, not for null alone, excellent for noisy generics. Not JavaScript's var.

88. String methods added in recent versions?

strip() (unicode-aware, 11), isBlank(), lines(), repeat(), formatted, describeConstable, indexOf overloads. Plus String.join, chars, codePoints - prefer these over manual StringTokenizer/index loops.

89. What is the HttpClient API?

Java 11's java.net.http.HttpClient: sync send and async sendAsync, HTTP/2 by default with 1.1 fallback, WebSockets, timeouts, async body handlers. Replaces URLConnection boilerplate for modern calls; reactive IO with BodyHandlers.ofPublisher.

90. Modules in brief?

JPMS (9+): packages grouped into modules with explicit requires/exports - strong encapsulation (reflective access to non-exported packages fails by default), smaller runtimes (jlink), faster startup potential. Classic classpath remains "unnamed module" - migration is gradual, most apps still run fine there.

JDBC & Database

91. JDBC flow in order?

Load driver (auto via ServiceLoader now) → DriverManager.getConnection/DataSource → PreparedStatement → executeQuery/executeUpdate → ResultSet loop → close resources (try-with-resources). Always use parameters via setXxx, never string concatenation.

92. PreparedStatement vs Statement?

Precompiled plan + bound parameters: safe from SQL injection, faster on reuse, type-safe setters. Statement invites injection and re-parses every time. For batch inserts: addBatch/executeBatch round-trips one message instead of N.

93. What does setAutoCommit(false) give you?

Manual transaction control: commit at a logical unit of work, rollback on failure, so partial writes never persist. Add savepoints for nested rollback. Today you'd often let the framework (JTA/Spring) manage it, but the underlying mechanism is the same.

94. ResultSet types - scrollable and updatable?

Default forward-only, read-only. TYPE_SCROLL_INSENSITIVE allows absolute/relative navigation (snapshot), SCROLL_SENSITIVE sees others' changes (driver support varies). CONCUR_UPDATABLE lets updateRow/deleteRow - convenient, but usually better to UPDATE via SQL.

95. What is a DataSource vs DriverManager?

DataSource is the modern entry point: pooling (HikariCP), JNDI lookup, driver configuration in one place - connections are reused instead of opened per request. DriverManager creates raw single-use connections; app servers and pools all expose a DataSource.

96. What causes SQLIntegrityConstraintViolationException?

PK/FK/unique/check violations crossing your SQL - duplicate insert, orphan reference, null in not-null. Handle by mapping to 409/conflict, not by retrying blindly; use upsert (MERGE/ON CONFLICT) when duplicates are expected concurrency.

Web: Servlets, JSP, Spring, Hibernate

97. Servlet lifecycle?

Container loads the class and creates one instance → init() once → service() per request dispatched to doGet/doPost/... (concurrent, on many threads - keep fields clean) → destroy() on undeploy. One instance, many threads is the mental model that prevents subtle bugs.

98. What is session tracking?

State across requests: HttpSession with the JSESSIONID cookie (URL rewriting via encodeURL for cookie-less clients), hidden form fields, or tokens. Sessions live server-side; scale-out means sticky sessions or a shared store (Redis).

99. Filter vs Interceptor vs Listener?

Filter (javax/jakarta.servlet) wraps requests/responses before the servlet - auth, gzip, CORS. Interceptor (Spring MVC) works inside the DispatcherServlet chain around handler methods - AOP-ish concerns. Listener reacts to lifecycle events (session created, context initialized).

100. MVC in Spring - request path?

Request → DispatcherServlet → handler mapping → controller method (with bound @RequestParam/@RequestBody) → ModelAndView/@ResponseBody → view resolver (templates) or message converters (JSON) → response. Services and repositories sit below the controller - controllers stay thin.

101. Spring IoC and DI in one paragraph?

The container builds objects and wires collaborators instead of you calling new: @Component-scanned beans in a registry, constructor injection by default, AOP proxies for @Transactional. Benefits: loose coupling, swappable implementations (test doubles), lifecycle/transaction declaratively.

102. What does @Transactional actually guard?

It proxies the bean and opens a transaction around the method (default rolls back on RuntimeException only). Pitfalls: self-invocation bypasses the proxy, private methods don't trigger it, checked exceptions need rollbackFor=, and don't hold a transaction across HTTP calls or heavy processing.

103. Spring Boot's magic?

Auto-configuration: starter dependencies plus @Conditional rules decide datasource, web server, Jackson, actuator setup for you - embedded Tomcat, externalized config (yaml/env/profiles), production-ready health endpoints. No XML, minimal boilerplate - the "convention over configuration" of Spring.

104. Hibernate vs JPA?

JPA is the specification (annotations, EntityManager, JPQL). Hibernate is the leading implementation plus extras (Second-level cache, Criteria API polish, HQL refinements). You code to JPA (@Entity, repositories) and can swap providers; vendor APIs leak only when you opt in.

105. What is the N+1 select problem?

One query for parents, then N lazy queries for each parent's children - the classic ORM performance bug. Fixes: join fetch/EAGER judiciously, @EntityGraph, batch fetch (@BatchSize), or a projection query. Watch SQL logs in tests to catch it early.

106. Hibernate session and identity?

The Session (EntityManager) is a per-transaction unit of work: first-level cache keeps identity - the same PK returns the same instance while the session lives. save/persist assigns the id, merge copies state onto a detached instance, detach/clear leaves the session.

Design, Testing & Behavioral

107. Singleton - pitfalls?

Global mutable state, hidden coupling, testability loss, classloader issues in app servers, eager init cost. If needed: enum singleton or holder id - but prefer scoped beans/dependency injection; most "singletons" are just one-per-container services.

108. Strategy and Factory in one line each?

Strategy: inject/swap the algorithm behind a stable interface (comparators, payment providers). Factory: centralize creation so callers don't know the concrete type - returns the right implementation from a hint/config.

109. What makes code testable?

Small units with injected dependencies, no statics/singletons/time/network inside core logic, deterministic inputs (inject Clock/Random), explicit outputs instead of hidden side effects, and seams for fakes (interfaces, constructors). Then tests stay fast and boring.

110. Unit vs integration test?

Unit: one class/method with fakes, milliseconds, no IO - describes design. Integration: real collaborators (DB, web container, broker) - verifies wiring and SQL. Both needed; the pyramid is many units, fewer integration, rare E2E. Flaky integration tests usually mean leaked state or time dependence.

111. How do you debug a hung Java service?

jstack <pid> (or jcmd Thread.print) several times - look for threads stuck in the same frame, BLOCKED/waiting states, deadlock section. Then heap histograms (jmap -histo), async-profiler for CPU, GC logs for pause mysteries. Reproduce with a thread dump before touching code.

112. What would you check for a sudden memory leak in production?

Heap after GC keeps growing? Take jcmd <pid> GC.heap_dump (or JFR recording), find dominator tree: static collections, caches without bounds, ThreadLocals in pools, listener leaks, ClassLoader accumulation (deployment reloads). Compare histograms across time to spot the growing class.

113. serialVersionUID - what for?

Guards serialization compatibility: same UID = streams compatible despite field evolution (add/remove with care); different UID → InvalidClassException. Generate explicitly (serialver, IDE) - the default computed UID breaks with almost any class edit.

114. Lamda capture rules?

Lambdas may only capture (effectively) final locals and the enclosing instance's fields/methods - no mutable local capture (pre-8; still true for locals). Mutation goes through single-element arrays or holders. Parameters and caught variables follow the same effectively-final rule.

115. Default methods - why do they exist?

To evolve interfaces without breaking implementors: Java 8 added Iterator.remove, Collection.stream this way. Rules: class methods win over interface defaults; more specific interface wins; otherwise you must override explicitly. Also the tool for multiple inheritance of type.
