Threads & Concurrency Interview Questions

Threads & Concurrency - topic bank

Topic bank #3 of the Interview Prep hub. Deep dive tutorial: Thread tutorial · Archive: Thread classes.

1. Thread vs Runnable vs Callable?

Thread is a class owning a native thread + start/join; Runnable is a unit of work returning nothing; Callable returns a value/throws, run by executors giving a Future. Modern default: implement Runnable/Callable and hand to an ExecutorService - manual new Thread only for demos or one-off background tasks (and virtual threads change even that calculus).

2. Lifecycle states and legal transitions?

NEW → RUNNABLE (start) → {BLOCKED | WAITING | TIMED_WAITING} → RUNNABLE → TERMINATED. BLOCKED = waiting for a monitor; WAITING = wait/join/park without timeout; TIMED_WAITING = with timeout. Illegal: start twice, start a dead thread. interrupt() only sets a flag or throws InterruptedException if blocked.

3. What exactly does synchronized guarantee?

Mutual exclusion + visibility: at monitor entry, read fresh values; at exit, flush writes (happens-before edge). It locks on an object: synchronized method → this (static methods → Class object). Reentrant, so nested calls are fine. Only one thread per lock at a time - the basis of "atomic section" reasoning.

4. volatile - what it does and does NOT do?

Guarantees visibility (reads/writes go to main memory, establishing happens-before between writer and reader) and prevents reordering around the access. Does NOT make compound operations atomic - count++ on volatile is still racy. Correct for status flags and safe publication (immutable refs); wrong for counters (use AtomicInteger/LongAdder).

5. What is the Java Memory Model in one answer?

The contract that defines when writes by one thread are visible to another: happens-before edges come from synchronized blocks, volatile accesses, thread start/join, executor handoffs, final field freeze, and the atomic package. Without an edge, threads may cache values forever. Every concurrency bug root cause: missing happens-before.

6. wait/notify vs Condition vs BlockingQueue?

wait/notify: requires holding the monitor, always in a while loop guarding the predicate, notifyAll unless proven single-consumer. ReentrantLock.newCondition: multiple wait sets, timed waits, interruptible - same loop discipline. BlockingQueue: wraps all of it - use this unless you genuinely need custom signaling.

7. Race condition - give a subtle one.

if (map.containsKey(k)) map.put(k, v); on HashMap from two threads - check-then-act race plus structural corruption (Java 8 can still create corruption in resize races). Fix: ConcurrentHashMap.merge/computeIfAbsent. Lazy-init singleton without synchronization is the other classic (use holder idiom/enum).

8. Deadlock: the four conditions and practical prevention?

Coffman: mutual exclusion, hold-and-wait, no preemption, circular wait. Prevention: global lock ordering (always lock A before B - document it), lock timeouts (tryLock), lock-free structures, single lock per object graph, avoid calling foreign code/back to caller holding a lock. Detection: jstack/ThreadMXBean shows "Found one Java-level deadlock".

9. Livelock and starvation?

Livelock: threads stay active but keep yielding/retrying in lockstep - progress never happens (polite retry loops). Starvation: a thread never gets the lock/CPU (unfair locks, priority). Fixes: randomized back-off, fair locks (new ReentrantLock(true) - costlier), priority hygiene, avoid unbounded nested locking.

10. Asymmetric lock usage - what's the bug?

Thread A locks this (synchronized method), thread B locks a private helper object, or exits early without unlocking (ReentrantLock not in finally). Result: silent non-protection. Rule: one lock object per invariant, always unlock in finally, never leak the lock object to outside code (use a private final field).

11. How do Atomic classes work - CAS?

Compare-and-swap loop: read current, compute new, swap only if still current, retry otherwise. On modern CPUs a lock-prefixed instruction; JVM may use intrinsics. AtomicInteger.incrementAndGet is a CAS loop; LongAdder distributes across cells (faster under contention, sum not atomic at a point); AtomicReference enables lock-free data structures (plus AtomicStampedReference for ABA).

12. ABA problem?

A value changes A→B→A between your read and CAS; CAS succeeds but the intermediate work may have invalidated invariants (classic in lock-free stacks). Fix: version stamp (AtomicStampedReference), or design structures where ABA is harmless (immutable nodes).

13. Executors: what the framework hides?

Thread creation, pooling, task queuing, shutdown, result plumbing. Key factories: newFixedThreadPool (bounded workers, unbounded queue - risk), newCachedThreadPool (unbounded threads - risk), newScheduledThreadPool, newSingleThreadExecutor. Executors are automatically wrapped (newFixedThreadPool has unbounded queue → memory risk). Best practice: construct ThreadPoolExecutor explicitly with bounded queue + rejection policy + named threads, or use virtual threads (21) for blocking workloads.

14. How do you stop an executor properly?

shutdown(): no new tasks, drain queue. shutdownNow(): interrupt running tasks, return queued list. Await termination with timeout; handle rejected tasks; register as app-lifecycle closeable (use try-with-resources, ExecutorService implements AutoCloseable since 19). Never leave pools unclosed in web apps - redeploy leaks threads.

15. Future vs CompletableFuture?

Future: blocking get, no composition, no callbacks, cancellation cooperative. CompletableFuture: non-blocking chains (thenApply, thenCompose, thenCombine), error handling (handle, exceptionally), anyOf/allOf, timeouts (Java 9 orTimeout/completeOnTimeout). Rules: always specify the executor, handle exceptions in every branch, don't mix blocking get into pipelines.

16. ThreadLocal - what is it and when does it leak?

Per-thread variable storage (key = thread, value in a per-thread map). Leaks in thread pools: the pool thread outlives the task, keeping the value (and its classloader) alive; remove() in a finally block is mandatory. Modern replacements: pass parameters explicitly, use framework scoping (request-scoped beans), or ScopedValue (21 preview) with structured concurrency.

17. fork/join vs parallel streams?

ForkJoinPool: work-stealing pool for recursive divide-and-conquer tasks (RecursiveTask), tuned for CPU-bound work. Parallel streams share the common pool by default (change via custom pool trick is discouraged) - only for large, independent, no-blocking-I/O workloads with order-independent operations. Benchmarks regularly show parallel streams losing for small inputs and I/O.

18. Producer-consumer: three implementations?

(1) BlockingQueue + threads/executors - production answer. (2) synchronized + wait/notify with while loop. (3) ReentrantLock + two Conditions (notFull/notEmpty) - most explicit. Also mention bounded blocking = back-pressure (protects memory under overload).

19. What's in java.util.concurrent besides pools and queues?

Concurrent collections (CHM, CopyOnWrite, SkipList), synchronizers (CountDownLatch, CyclicBarrier, Semaphore, Exchanger, Phaser), atomics, locks (ReentrantLock/ReadWriteLock/StampedLock), ThreadLocalRandom, and higher-level (Future, CompletableFuture, Executors). Version additions: 9 reactive-flow (Flow), 19 structured concurrency preview, 21 virtual threads + scoped values preview.

20. CountDownLatch vs CyclicBarrier vs Semaphore?

Latch: one-shot countdown; threads await until it hits zero (start gun / wait for N initializations). Barrier: reusable rendezvous - N parties each wait for the others (phased algorithms). Semaphore: permits - limit concurrency (e.g., 10 DB connections) without owning threads; acquire/release and tryAcquire with timeout for graceful degradation.

21. ReadWriteLock vs StampedLock edge cases?

ReadWriteLock: readers share, writers exclusive; beware write starvation (fair mode) and lock downgrade subtlety (can acquire read while holding write). StampedLock: optimistic reads (validate stamp), NOT reentrant, no condition support - fastest for read-heavy, but the optimistic path must be coded with a fallback and locks can deadlock if misused.

22. What's the deal with Thread.stop/suspend/resume?

Deprecated/removed: stop releases monitors at arbitrary points (corrupted state), suspend/resume can deadlock (suspended thread holding lock). Cooperative cancellation instead: interrupt + check flag/InterruptedException, or a volatile boolean run flag; executors' Future.cancel(true) does exactly that (interrupt the worker).

23. What does Thread.interrupt() actually do?

If the thread is in a blocking call (sleep, wait, join, interruptible I/O, some NIO), it throws InterruptedException and the flag clears. Otherwise it just sets the interrupt flag - your loop must check Thread.currentThread().isInterrupted(). Swallowing the exception and not re-setting the flag is a classic bug.

24. How would you unit-test concurrency?

Test invariants/determinism first (isolate logic). Then stress with latches/barriers coordinating threads, thousands of iterations, assertions on the final state; use JMH for performance claims, not stopwatch tests. Concurrency bugs rarely reproduce on demand - treat flaky tests as bugs (never rerun-to-green), and prefer designs that remove shared mutable state.

25. What are virtual threads (Java 21)?

JVM-scheduled (not OS) threads; millions possible; cheap to block - blocking calls unmount the virtual thread from its carrier. Best for thread-per-task I/O-heavy servers (Tomcat/Spring Boot 3.2 opt-in; JDK 21 has a small pool of carrier threads). Pitfalls: pinning by synchronized blocks/native frames (fixed in 24 for some cases), CPU-bound work doesn't benefit, and thread-local caches explode - revisit pooling assumptions.

26. Thread priority and daemon threads - useful?

Priorities are hints; behavior is OS-dependent (effectively useless for correctness). Daemon threads don't keep the JVM alive - used for housekeeping; NEVER run critical work on a daemon (it dies mid-flight at shutdown). Executor threads are non-daemon by default - shutdown hooks or try-with-resources handle termination.

27. What is safe publication?

Getting a reference to an object to another thread without tearing/partial-final-field visibility. Ways: initialize in a static initializer, store into a volatile/final field, lock-protect it, or hand over via a concurrent collection. Without publication safety, another thread can see a half-constructed object (final fields of a properly-published object are frozen by the JMM).

28. Explain happens-before with an example a novice can follow.

Think of a whiteboard: only when there's a "handshake" (lock release-acquire, volatile write-read, thread start/join) does one thread's whiteboard edits become guaranteed-visible to the other. Without the handshake the reader may clutch their private notes (CPU cache) - correct code always inserts the handshake between writer and reader.
